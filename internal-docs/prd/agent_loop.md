# Agent Loop 增强 — 产品需求文档 (PRD)

## 背景与目标

### 背景

jcode 是一个基于 Go 语言的 CLI 编码助手，采用 Eino 框架 + BubbleTea TUI 架构。当前的 Agent Loop 实现（`internal/runner/runner.go`）采用同步迭代模式，功能覆盖了基本的工具调用、流式输出和 Todo 完成守护。

通过与 Claude Code (JS/TS) 的对比分析（参见 `docs/analyse/agent_loop.md`），当前实现在以下关键领域存在差距：

| 能力 | 当前状态 | 目标状态 |
|------|---------|---------|
| 上下文管理 | 无压缩，长对话溢出 | 自动摘要 + 分级压缩 |
| 错误恢复 | 仅 API 3 次重试 | 分层降级（MaxOutput → Snip → Fallback） |
| 代理并发 | 顺序执行 subagent | 多 subagent 并行 + coordinator |
| 成本控制 | 仅日志记录 token | 实时预算控制 + 超限阻断 |
| 流式架构 | 同步阻塞迭代 | Go channel 异步流式 |

### 目标

1. 提升长对话场景的稳定性和可用性
2. 降低 token 浪费，实现可控的成本管理
3. 支持复杂任务的并行分解与协调
4. 增强错误场景下的自动恢复能力
5. 保持与现有 Eino 框架和 BubbleTea TUI 的兼容性

## 用户故事

### US-1: 长对话不丢失上下文

> 作为一个开发者，我希望在长时间的编码会话中，助手能自动管理上下文窗口，而不是因为 token 超限导致对话中断或丢失关键信息。

**验收标准**:
- 当对话 token 接近模型上下文限制的 80% 时，自动触发历史压缩
- 压缩后保留最近 N 条用户消息和最近的工具调用结果
- 用户无感知，对话自然延续

### US-2: 错误自动恢复

> 作为一个开发者，我希望当模型输出被截断或 API 返回错误时，助手能自动尝试恢复，而不是直接终止对话。

**验收标准**:
- 模型输出被截断（MaxOutputTokens）时，自动续写
- 上下文过长时，自动压缩并重试
- 主模型不可用时，自动降级到备用模型
- 所有自动恢复操作对用户可见（状态提示）

### US-3: 复杂任务并行处理

> 作为一个开发者，我希望助手能将复杂任务分解为多个子任务并行执行，加速任务完成。

**验收标准**:
- 支持 coordinator 模式，主代理可以 spawn 多个 worker
- worker 间无状态依赖时并行执行
- coordinator 汇总各 worker 结果后生成最终响应
- 用户可在 TUI 中看到各 worker 的执行状态

### US-4: Token 预算控制

> 作为一个开发者（或团队管理者），我希望能设置每次对话或每个任务的 token 预算，防止意外的高成本消耗。

**验收标准**:
- 支持在配置中设置 `max_tokens_per_turn` 和 `max_cost_per_session`
- 接近预算上限时发出警告
- 达到上限时优雅停止，不丢失已有输出
- TUI 实时显示当前 token 消耗和剩余预算

### US-5: 流式架构升级

> 作为一个开发者，我希望助手的响应延迟更低，UI 渲染更流畅。

**验收标准**:
- 使用 Go channel 替代同步 `iterator.Next()` 的阻塞模式
- 支持用户中途取消正在进行的请求
- 流式事件解耦：事件生产与消费独立，不互相阻塞

## 功能需求

### P0 — 核心（必须实现）

| 编号 | 功能 | 描述 | 关联用户故事 |
|------|------|------|-------------|
| F-001 | 上下文压缩引擎 | 检测 token 使用率，自动触发历史消息摘要压缩，保留关键消息 | US-1 |
| F-002 | 分层错误恢复 | 实现 MaxOutput 续写 → 上下文压缩重试 → 备用模型降级的三级恢复 | US-2 |
| F-003 | Token/Cost 实时追踪 | 每条消息级别的 token 和成本累计，TUI 实时展示 | US-4 |
| F-004 | 预算阈值控制 | 基于配置的 token/cost 预算，接近阈值警告，达到阈值优雅停止 | US-4 |

| 编号 | 功能 | 描述 | 关联用户故事 |
|------|------|------|-------------|
| F-005 | Channel 流式架构 | 使用 `chan Event` 替换同步迭代器，支持多消费者和取消操作 | US-5 |
| F-006 | 请求取消支持 | 用户可通过 TUI 或快捷键取消正在执行的 agent 请求 | US-5 |
| F-007 | Coordinator 模式 | 主代理作为协调者，分解任务并 spawn 多个 worker subagent 并行执行 | US-3 |
| F-008 | Worker 状态追踪 | TUI 展示每个 worker subagent 的执行状态（pending/running/done/failed） | US-3 |

|------|------|------|-------------|
| F-009 | 智能压缩策略 | 基于消息重要性评分的选择性压缩（保留 error 消息、用户确认等关键节点） | US-1 |
| F-010 | 会话预算报告 | 会话结束后生成 token/cost 使用报告 | US-4 |
| F-011 | 压缩感知会话恢复 | `--resume` 恢复会话时正确处理压缩边界 | US-1 |

## 非功能需求

### 性能

| 指标 | 要求 |
|------|------|
| 首 token 延迟 | 上下文压缩不增加超过 500ms 的额外延迟 |
| 流式吞吐 | TUI 渲染帧率 ≥ 30fps，无卡顿感 |
| 并发 subagent | 支持同时运行 ≥ 3 个 worker subagent |
| 内存占用 | 长对话（>100 轮）内存增长 < 50MB |

### 可靠性

| 指标 | 要求 |
|------|------|
| 错误恢复成功率 | 分层恢复覆盖 90% 以上的可恢复错误 |
| 数据安全 | 上下文压缩不丢失用户确认、工具审批等关键信息 |
| 会话持久性 | 压缩和恢复不破坏 JSONL 会话文件的完整性 |

### 兼容性

| 指标 | 要求 |
|------|------|
| Eino 框架 | 基于 Eino ADK 的 `ChatModelAgent` 和 `ChatModelAgentMiddleware` 扩展 |
| BubbleTea | 新的 TUI 消息类型通过 `tea.Msg` 接口兼容现有 TUI 架构 |
| 配置文件 | 新增字段向后兼容，旧配置文件无需修改即可工作 |
| Go 版本 | Go 1.21+ |

### 可观测性

| 指标 | 要求 |
|------|------|
| 日志 | 所有压缩、恢复、预算操作记录到 `~/.jcoding/debug.log` |
| Langfuse | 压缩事件和错误恢复事件作为 span 上报 |
| TUI 状态 | 用户可通过状态栏看到当前上下文使用率和预算消耗 |

## 成功指标

| 指标 | 基线（当前） | 目标 | 衡量方式 |
|------|------------|------|---------|
| 长对话成功率 | 50轮后频繁上下文溢出 | 200+ 轮无中断 | 自动化测试 + 用户反馈 |
| 错误恢复率 | 0%（直接失败） | ≥ 80% 可恢复错误自动恢复 | 错误日志统计 |
| Token 浪费率 | 无法衡量 | 通过压缩减少 30% 冗余 token | token 追踪数据对比 |
| 复杂任务完成时间 | 只能串行 | 并行模式缩短 40%+ | 任务耗时对比 |
| 用户满意度 | 无基线 | 预算控制 + 状态可见提升信任度 | 用户调研 |

## 术语表

| 术语 | 定义 |
|------|------|
| Agent Loop | 代理主循环，处理用户消息→模型推理→工具调用→结果反馈的完整流程 |
| 上下文压缩 (Context Compaction) | 将历史消息摘要化以减少 token 占用，延长有效对话轮次 |
| 分层错误恢复 (Layered Error Recovery) | 按严重程度分级的错误处理策略：续写→压缩→降级 |
| Coordinator 模式 | 主代理负责任务分解和结果汇总，worker subagent 负责并行执行子任务 |
| Token 预算 | 预设的 token 消耗上限，用于控制单次对话或单个任务的成本 |
| Eino | CloudWeGo 开源的 AI 应用开发框架，提供 ChatModelAgent 等核心抽象 |
| BubbleTea | Charm 社区的 Go TUI 框架，基于 Elm Architecture |
