# 权限系统增强 — 产品需求文档 (PRD)

## 背景与目标

### 背景

jCode 当前的权限系统采用简化的二元模式（Manual/Auto），配合硬编码的工具白名单和安全命令前缀列表进行审批控制。核心实现位于 `internal/runner/approval.go`，通过 `internal/agent/middleware.go` 中间件在工具执行前拦截。

现有系统的主要局限性：

| 局限 | 描述 |
|------|------|
| **无持久化** | 权限规则仅存在于内存中，会话结束后丢失，用户每次启动都需重新审批 |
| **规则粒度不足** | 仅支持"全部通过"或"逐个审批"，缺少 deny 规则和正则匹配 |
| **MCP 无权限管控** | MCP 动态加载的外部工具无独立权限策略 |
| **同步阻塞审批** | 所有审批通过 TUI 同步阻塞，无法并行处理 |
| **无组织级策略** | 缺乏企业/团队层面的统一权限配置能力 |

### 目标

构建层级化、可持久化、可扩展的权限管理系统，提升安全性与使用效率，同时保持 CLI 工具的轻量特性。

**核心指标**：
- 减少重复审批次数 ≥60%（通过持久化规则和模式匹配）
- MCP 工具覆盖率 100%（所有外部工具纳入权限管控）
- 审批响应延迟 < 200ms（非用户交互路径）

## 用户故事

### US-1: 持久化权限偏好
> 作为一个频繁使用 jCode 的开发者，我希望我批准过的工具权限能够被记住，这样下次启动时不需要重复审批同样的操作。

**验收标准**:
- 用户可选择将审批决定保存到用户级/项目级配置
- 保存的规则在下次启动时自动加载
- 提供 `coding permissions list/reset` 命令管理已保存规则

### US-2: 细粒度权限控制
> 作为一个安全意识较强的开发者，我希望能够精确地允许或拒绝特定工具的特定操作模式（如：允许 `execute` 执行 `go test` 但拒绝 `rm -rf`），而不是只有全通过或逐个审批。

**验收标准**:
- 支持 allow/deny/ask 三种规则类型
- 支持工具名 + 参数正则表达式匹配
- deny 规则优先级高于 allow

### US-3: MCP 工具权限管控
> 作为一个使用多个 MCP 服务器的开发者，我希望能够分别控制每个 MCP 服务器及其工具的权限，防止不信任的服务器执行危险操作。

**验收标准**:
- 每个 MCP 服务器有独立的权限配置
- 支持服务器级（所有工具）和工具级权限
- 新增 MCP 服务器默认要求审批

### US-4: 高效异步审批
> 作为一个处理复杂任务的用户，当 Agent 并行调用多个工具时，我希望审批请求能够排队展示，而不是阻塞整个流程。

**验收标准**:
- 并行工具调用生成审批队列
- 用户可批量审批同类请求
- 已有规则匹配的请求自动通过，不进入队列

### US-5: 组织策略限制
> 作为一个团队管理者，我希望能够为团队设置统一的权限策略，限制某些高危操作，即使开发者个人配置允许也应被策略阻止。

**验收标准**:
- 支持通过配置文件定义组织级策略
- 策略优先级高于所有用户规则
- 策略变更无需重启即可生效

## 功能需求

### P0 — 必须实现

#### F-1: 持久化规则存储

**描述**: 在 `~/.jcoding/` 下新增 `permissions.json` 文件，存储用户权限规则。

**规则层级**（优先级从高到低）：

| 层级 | 文件位置 | 作用域 | 版本控制 |
|------|---------|--------|---------|
| 会话级 | 内存 | 当前会话 | 否 |
| 项目级 | `<project>/.jcoding/permissions.json` | 当前项目 | 可选 |
| 用户级 | `~/.jcoding/permissions.json` | 全局 | 否 |

**规则合并逻辑**: 会话级 > 项目级 > 用户级。deny 规则在每层内优先于 allow。

**CLI 管理命令**:
```
coding permissions list              # 列出所有生效规则
coding permissions add <规则>        # 添加规则
coding permissions remove <ID>       # 删除规则
coding permissions reset             # 清空所有规则
```

#### F-2: 三层规则系统 (allow/deny/ask)

**描述**: 扩展当前的二元审批模式为三层规则系统。

**规则结构**:
```json
{
  "rules": [
    {
      "id": "rule-uuid",
      "tool": "execute",
      "action": "allow",
      "args_pattern": "^go (test|build|vet)",
      "scope": "user",
      "created_at": "2026-04-10T00:00:00Z"
    },
    {
      "id": "rule-uuid",
      "tool": "execute",
      "action": "deny",
      "args_pattern": "rm\\s+-rf",
      "scope": "project"
    }
  ]
}
```

**规则评估流程**:
1. 收集所有匹配的规则（工具名 + 参数正则匹配）
2. 按优先级排序：deny > allow > ask
3. 同优先级按层级排序：会话 > 项目 > 用户
4. 无匹配规则时退回默认行为（当前白名单逻辑）

#### F-3: MCP 工具权限管控

**描述**: 为 MCP 动态加载的工具引入独立权限配置。

**命名约定**: `mcp__<serverName>__<toolName>`

**配置示例** (在 `permissions.json` 中):
```json
{
  "rules": [
    {
      "tool": "mcp__github__create_issue",
      "action": "allow",
      "scope": "user"
    },
    {
      "tool": "mcp__filesystem__*",
      "action": "ask",
      "scope": "project"
    }
  ]
}
```

**默认策略**: MCP 工具首次调用时，如无匹配规则，默认触发 ask（用户审批）。

### P1 — 应当实现

#### F-4: 异步批准队列

**描述**: 将同步阻塞的审批流程改为异步队列模式。

**核心行为**:
- 工具调用产生审批请求时，放入队列而非立即阻塞
- TUI 按队列顺序展示待审批项
- 已有规则匹配的请求旁路队列直接通过
- 支持"全部允许"/"全部拒绝"批量操作
- 队列深度上限 50，超出时暂停新工具调用

**并行处理**: Agent 在等待审批时可继续执行不需要审批的工具调用。

#### F-5: 审批时保存规则提示

**描述**: 在用户审批时，提供"记住此决定"选项。

**TUI 交互**:
```
🔧 Tool: execute
   Command: go test ./...

  [y] 允许  [n] 拒绝  [a] 允许并记住(项目级)  [A] 允许并记住(用户级)
```

#### F-6: 路径权限增强

**描述**: 扩展当前 `isWithinWorkpath` 为可配置的路径白名单。

**配置**:
```json
{
  "allowed_paths": [
    "~/go/pkg/mod",
    "/usr/local/include"
  ]
}
```

### P2 — 可选实现

#### F-7: 组织策略限制 API

**描述**: 支持从本地配置文件加载组织级策略。

**策略文件**: `~/.jcoding/policy.json`

```json
{
  "version": 1,
  "deny_rules": [
    {
      "tool": "execute",
      "args_pattern": "curl.*\\|.*sh",
      "reason": "禁止管道执行远程脚本"
    }
  ],
  "require_approval": ["write", "edit"],
  "max_auto_approve_count": 100
}
```

**特性**: 策略文件优先级高于所有用户/项目规则，deny 不可覆盖。

#### F-8: 权限审计日志

**描述**: 记录所有权限决策到日志文件，便于安全审计。

**日志格式** (JSONL):
```json
{"ts":"2026-04-10T10:00:00Z","tool":"execute","args":"rm -rf /tmp/test","decision":"deny","rule_id":"rule-uuid","source":"project"}
```

**文件位置**: `~/.jcoding/audit.log`

#### F-9: 命令分类器（可选）

**描述**: 参考 Claude Code 的分类器思路，为 execute 工具的命令参数提供智能分类。

初期可基于规则引擎实现（非 LLM），后续可扩展为 LLM 驱动的分类。

## 非功能需求

### NFR-1: 性能
- 规则评估延迟 < 5ms（单次匹配）
- 权限文件加载 < 50ms（启动时）
- 正则编译缓存，避免重复编译

### NFR-2: 安全性
- 权限文件权限设为 `0600`（仅用户可读写）
- deny 规则不可被 allow 覆盖（同层级内）
- 策略规则不可被任何用户规则覆盖
- 路径检查防止符号链接逃逸

### NFR-3: 兼容性
- 向后兼容现有 `config.json` 配置
- 无权限文件时退回当前硬编码白名单行为
- 现有 `ApprovalState` 接口保持兼容

### NFR-4: 可维护性
- 权限模块独立包，与 agent/runner/tui 低耦合
- 规则存储使用接口抽象，便于后续扩展为远程存储
- 完备的单元测试覆盖率 ≥ 80%

### NFR-5: 用户体验
- 新增功能不增加必需配置项（零配置可用）
- 权限冲突时输出清晰的诊断信息
- TUI 审批交互响应流畅，无闪烁

## 成功指标

| 指标 | 目标值 | 度量方式 |
|------|--------|---------|
| 重复审批减少率 | ≥ 60% | 对比有/无持久化规则时用户审批次数 |
| MCP 工具权限覆盖率 | 100% | 所有 MCP 工具调用经过权限检查 |
| 规则评估性能 | P99 < 5ms | 基准测试 |
| 零配置兼容 | 100% | 无权限文件时行为与现有系统一致 |
| 用户满意度 | ≥ 4/5 | 用户反馈调查 |
| 权限模块测试覆盖率 | ≥ 80% | `go test -cover` |
